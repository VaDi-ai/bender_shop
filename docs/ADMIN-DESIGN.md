## 0. Принципы

1. **БД — единственный источник правды.** Google-таблица и веб-админка — два *редактора* поверх одной истины, а не два хранилища. Витрина читает только БД.
2. **Управление работает из обоих редакторов.** Владелец продолжает жить в таблице (цены/наличие 10+ раз в день), staff получает веб для всего остального. Ни один сценарий не требует «лезть в код».
3. **У каждого поля есть канал редактирования** (см. §1). Синк и админка не воюют: у поля либо один хозяин, либо детерминированный last-write-wins.
4. **Ничего не удаляем — переиспользуем.** «Мёртвые» модели ценового контура (Supplier, SupplierPrice, PriceAlias, PriceChange) — это готовая схема флагманской фичи «разбор прайсов» (§7). Рудименты склада (Reservation, Product.stock/reserved, ручные StockMovement) прячем из UI, из схемы не выносим.
5. **Каждая мутация из админки журналируется** (AuditLog, §5.8) — закрывает «кто что менял» из дерева §8.

Каркас UI — по мокапу: мобильная Mini App с 5 табами **Что сегодня / Цены и поставщики / Витрина / Товары / Ещё** (тот же стек, что витрина: Telegram WebApp + initData-auth).

## 1. Модель владения полями (утверждено)

### 1.1 Матрица

| Канал | Поля | Поведение синка | Поведение админки |
|---|---|---|---|
| **Только таблица** | закупочная и розничная цена (через цепочку наценки), количество/наличие, атрибуты варианта (страна, память, цвет, SIM…), `fullName`, состав вариантов | зеркалит лист → БД каждый прогон (как сейчас) | **read-only**: показывает со значком «📄 правится в таблице» и deep-link на лист |
| **Только админка** | hero-баннеры, ручные хиты (`isFeatured`), тексты витрины (маркиза, футер, ярлыки, юр-доки), акции, рассылки, скрытие товара, справочник стран/SIM, наценки | **не трогает вообще**; колонка «В хиты» в листе деприкейтится (см. §1.4) | полный CRUD |
| **Оба, last-write-wins** | описание, главное фото товара, бейдж, порядок (`sortOrder`) | по алгоритму §1.2 | правит + опциональная обратная запись в лист §1.3 |

### 1.2 Алгоритм LWW для общих полей: «снапшот листа + источник изменения»

Проблема: у ячейки Google-таблицы нет timestamp'а. Решение — паттерн, уже обкатанный в синке на `lastSyncedCostPrice`: **храним снапшот последнего синкнутого значения листа** и по нему отличаем «лист менялся» от «лист не менялся».

Для каждого общего поля F товара храним:
- `sheetSnapshot.F` — значение F в листе на момент последнего синка;
- `editMeta.F = { source: sheet|admin|bot|ai, at: <время>, by: <кто> }` — источник и время последнего изменения.

Прогон синка для поля F (S — значение в листе, P — снапшот, D — значение в БД):

| Случай | Условие | Действие |
|---|---|---|
| Лист не менялся | `S == P` | **D не трогаем** — правка админки живёт. Это ключевое отличие от текущего «зеркалим всегда» |
| Лист менялся | `S != P` | лист выигрывает: `D = S`, `P = S`, `editMeta.F = {source: sheet, at: now}`. Прежнее значение D — в AuditLog (можно вернуть одной кнопкой) |

Правка из админки: `D = value`, `editMeta.F = {source: admin, at: now, by: adminId}`, **снапшот P не трогаем** (иначе следующая правка листа не пройдёт).

Крайний случай (документируем, не боремся): владелец правит ячейку в 12:05, staff правит то же поле в админке в 12:30, синк в 13:00 видит `S != P` → выигрывает таблица, хотя правка админки «свежее» по часам. Время правки листа неизвестно, LWW считает его равным времени обнаружения. Смягчение: (а) writeback §1.3 сжимает окно конфликта до минут; (б) админка после перезаписи показывает на поле бейдж «перезаписано таблицей N мин назад» + «вернуть моё» (из AuditLog).

### 1.3 Обратная запись (writeback) для общих полей

Механизм в синке уже есть (`sheetWritebacks`: рекомендованная цена пишется в лист в том же прогоне). Расширяем до **очереди writeback'ов**:

- Правка общего поля в админке ставит задание в очередь `SheetWriteback` (§5.3): «в строки модели X записать колонку („Описание“ J / „Бейдж“ / „Порядок“) значение V».
- Воркер (или ближайший прогон синка) применяет пачкой, **адресуя строки по ключу `fullName` (колонка D), а не по номеру строки** — владелец сортирует и вставляет строки, rowIndex нестабилен.
- После успешной записи `sheetSnapshot.F = V` → таблица снова зеркало, конфликт исчезает по построению: владелец видит правку staff прямо в листе.
- Google API недоступен → задание остаётся в очереди с retry; поле в админке помечено «⏳ едет в таблицу».

Writeback включаем для: описание (колонка J — уже writeback-колонка синка), бейдж, порядок. Главное фото — без writeback (в листе нет колонки «главное фото», см. §5.4).

> **Решение владельца (§9.3): writeback контента — НЕ сразу.** Этап 1 и admin-only поля его не требуют. Общие поля на Этапе 2 сначала живут **без обратной записи** (только LWW §1.2); writeback включается отдельным шагом (Этап 2b) после проверки LWW на живых данных. Безопасность таблицы владельца важнее скорости. Ценовой writeback (§3.1, рекомендованная/закупочная) — не контентный, работает как работал.

### 1.4 Миграция колонки «В хиты»

Хиты по утверждённой матрице — только админка. Колонка «В хиты» в листе объявляется deprecated: синк перестаёт применять её значение, при наличии непустых ячеек пишет warning в журнал синка (§5.4 SyncRun) — «хиты теперь в админке». Через месяц колонку можно удалить из листа. «Бейдж» остаётся (канал «оба»).

## 2. Каркас: аутентификация, доступ, транспорт

Сейчас admin-HTTP — greenfield (2 эндпоинта под HMAC для CLI). Проектируем слой заново:

- **UI**: `/admin` — отдельная страница (Mini App), открывается из бота кнопкой «Админка» и напрямую из Telegram. Тот же паттерн, что витрина.
- **Auth**: `x-telegram-init-data` (валидация подписи уже реализована для Кабинета) + проверка по таблице **AdminUser** (§5.8), а не по env `ADMIN_IDS`. env остаётся bootstrap-списком (сидируется в AdminUser при старте). Роли: `owner` (всё) и `manager` (без §8 Система, без массовых удалений, без API-ключей).
- **Офбординг админа (рунбук).** Сид при каждом старте **реактивирует** любой ID, оставшийся в `ADMIN_IDS`, даже если запись выключили через веб. Поэтому снятие админа — строго два шага, в этом порядке: **(1) убрать ID из `ADMIN_IDS`** в Railway (передеплой), **(2) деактивировать запись** в AdminUser (веб/SQL). Только деактивация без правки env — небезопасно: следующий рестарт вернёт доступ.
- **API-неймспейс**: `/admin/api/*`, все мутации журналируются в AuditLog. Существующий HMAC-гейт (`requireAdminHmac`) остаётся для CLI-скриптов (фото-загрузка) — не смешиваем.
- **Rate-limit** на неймспейс + `SecurityLog` на отказ в доступе (событие уже есть).
- Бот-админка живёт параллельно и постепенно худеет: разделы, переехавшие в веб, в боте сворачиваются до ссылки «Открыть в админке».

## 3. Синхронизация: направления и разрешение конфликтов

### 3.1 Три потока

| Поток | Когда | Что |
|---|---|---|
| **Лист → БД** (есть) | ежечасно 11–20 МСК + кнопка «Обновить из таблицы» | цены/наличие/атрибуты/фото Q — зеркало; общие поля — по LWW §1.2 |
| **БД → лист, цены** (есть, расширяем) | в прогоне синка и при применении прайса §7 | рекомендованная (уже есть) **+ закупочная** — обе колонки после пересчёта цепочкой наценки |
| **БД → лист, контент** (новое) | очередь writeback §1.3 | описание / бейдж / порядок после правки в админке |

### 3.2 Сводка конфликтных сценариев

| Сценарий | Итог | Почему |
|---|---|---|
| Staff правит описание, лист не менялся | правка живёт, уезжает в лист writeback'ом | `S == P` → синк не трогает |
| Владелец правит описание в листе | лист выигрывает при ближайшем синке | `S != P` → sheet-канал свежее по определению LWW |
| Оба правят одно поле в одном часу | таблица выигрывает; в админке бейдж «перезаписано таблицей» + «вернуть моё» | время ячейки неизвестно (§1.2) |
| Правка admin-only поля (баннер, хит, акция) | синк вообще не смотрит на эти поля | канал «только админка» |
| Правка sheet-only поля из админки | невозможно — поле read-only в UI | канал «только таблица» |
| Строка/модель исчезла из листа | товар и варианты disabled (текущее поведение); admin-поля и editMeta сохраняются до возврата строки | наличие — sheet-канал |
| Владелец руками правит розничную цену в листе | уважается (существующая логика `sheetPrice != dbPrice`) | цены — sheet-канал, парсер §7 меняет только закупку |
| Writeback не доехал (API упал), владелец правит ту же ячейку | ячейка владельца выигрывает: задание в очереди устарело → при `S != P` отменяем writeback и принимаем лист | лист — интерфейс владельца, не ломаем его картину мира |

### 3.3 Наблюдаемость синка (дерево §3.3 «показать, что не синкнулось»)

Каждый прогон пишет строку **SyncRun**: когда, кто запустил (крон/админ), прочитано строк, создано/обновлено/disabled, **массив ошибок** (нераспознанные ячейки, дубли `fullName`, warning про «В хиты», упавшие writeback'и). В админке — «Синк: последний прогон, ошибки» на табе «Что сегодня» + полный журнал в «Ещё». Это замена сегодняшнего «смотри логи Railway».

## 4. Разделы админки → изменения схемы и API

Формат: по слоям дерева. **Схема** — только новые модели/поля (без кода), **API** — маршруты `/admin/api/*`. Существующие модели из аудита переиспользуются без изменений, если не сказано иное.

### 4.1 Что сегодня (дашборд)

Витрина фактов, ничего не редактирует: заказы за сегодня/вчера, выручка, последний SyncRun + ошибки, очередь «не узнал» парсера (§7), количество непрочитанных в инбоксе, ближайшие ДР клиентов (данные уже собираются — `Client.birthDate`).

- **Схема**: нет изменений (всё считается из существующих таблиц).
- **API**: `GET /admin/api/dashboard` (агрегат одним запросом).

### 4.2 Люди (дерево §1)

- **Клиенты**: список + карточка (роллапы есть в Client). Поиск/фильтры: VIP, с заказами, ДР в ближайшие N дней. Правка ФИО/телефона/email/статуса/заметок — перенос из CRM-топиков.
  - Схема: `Client.status` — сейчас статус живёт где-то в CRM-флоу; закрепить enum (`thinking | waiting_discount | refused | …`) полем на Client, если его нет; `ClientNote` (id, clientId, adminId, text, createdAt) — если заметки сейчас неструктурированные.
  - API: `GET/PUT /admin/api/clients`, `GET /admin/api/clients/:id`, `POST /admin/api/clients/:id/notes`.
- **Инбокс** (веб-лента переписки): единая лента по Message (9 470 строк, каналы уже размечены), ответ клиенту через существующие каналы (Telegram bot API / Avito / IG — отправка уже есть в CRM-флоу).
  - Схема: `Message.readAt DateTime?` + индекс (канал, readAt) — понятие «непрочитанное».
  - API: `GET /admin/api/inbox?unread=1&channel=`, `GET /admin/api/inbox/:clientId`, `POST /admin/api/inbox/:clientId/reply`.
- **Рассылки**: движок готов (BroadcastLog, отправка из бота). Веб-конструктор: текст+фото+кнопка, предпросмотр, «тест на себя», отложенная отправка.
  - Схема: `Broadcast` (черновики/расписание: id, title, text, photo, buttonText, buttonUrl, audience Json, scheduledAt?, status draft|scheduled|sending|done|cancelled, stats Json) — BroadcastLog остаётся журналом фактических отправок.
  - API: CRUD `/admin/api/broadcasts`, `POST …/:id/test`, `POST …/:id/schedule`.
- **Сегменты/теги** (🔴 в дереве): **решение владельца (§9.4) — поле из карточки убрать (скрыть), схему не удалять.** Выполняется на Этапе 3 вместе с остальным разделом «Люди».

### 4.3 Витрина (дерево §2)

- **Hero-баннеры**: CRUD + drag-порядок + вкл/выкл. Модель HeroBanner есть.
  - Схема: `HeroBanner.sortOrder`, `isActive` — сверить с фактической моделью, добить недостающее.
  - API: `GET/POST/PUT/DELETE /admin/api/banners`, `PUT /admin/api/banners/order`.
- **Маркиза и тексты витрины**: маркиза уже в `setting_marquee`. Футер (адрес/телефон/часы), ярлыки UI, юр-доки — сейчас хардкод; выносим в Setting-ключи `storefront_text_*`, витрина читает их с фолбэком на текущие тексты (страница не ломается при пустой настройке). Кнопка «Обновить сайт» = существующий `cache_version`.
  - API: `GET/PUT /admin/api/settings` (namespace-фильтр), `POST /admin/api/cache-reset`.
- **Хиты**: ручной список (`isFeatured`, admin-only §1.4) + текущий AI-подбор как «предложить» (существующий `/hits` флоу), staff подтверждает.
  - API: `PUT /admin/api/products/:id/featured`, `POST /admin/api/hits/suggest`.
- **Категории**: переименование, баннер, сторона текста (есть в модели), **ручное фото категории** и **порядок**.
  - Схема: `Category.sortOrder Int @default(0)`, `Category.imageSource enum auto|manual` (auto = «фото новейшей модели», manual = загруженное; закрывает «у AirPods нет фото»).
  - API: `GET/POST/PUT /admin/api/categories`, загрузка фото — существующий фото-пайплайн.
- **Секции главной** (конструктор раскладки) — «потом» по дереву; в схему не тащим до Этапа 4.

### 4.4 Товары (дерево §3)

- **Карточка**: описание/характеристики/бренд (общие/sheet-каналы по §1), бейдж (общий), AI-обогащение (есть), **главное фото**, **скрыть товар**, «одно фото на карточке».
  - Схема (Product): `mainPhotoUrl String?` (null → авто как сейчас: первое фото новейшего варианта), `isHidden Boolean @default(false)` (скрыт с витрины независимо от наличия; витринные выборки добавляют фильтр), `editMeta Json?`, `sheetSnapshot Json?` (§1.2).
  - API: `GET /admin/api/products?query=&hidden=&line=`, `GET/PUT /admin/api/products/:id` (PUT принимает только admin- и both-поля; sheet-поля игнорирует с 422), `PUT …/:id/main-photo`, `PUT …/:id/hidden`.
- **Предложения (варианты)**: атрибуты/цена/наличие — read-only (sheet). **Своё фото предложения**: админ-override поверх зеркала Q.
  - Схема (ProductVariant): `adminPhotoUrls String[]` — если непусто, витрина использует их вместо `photoUrls`; синк это поле не трогает (зеркало Q продолжает жить в `photoUrls`).
  - API: `PUT /admin/api/variants/:id/photos`.
- **Атрибуция SIM по стране** («США = eSIM only, Китай = 2 SIM» — сейчас врёт): справочник, который правит владелец.
  - Схема: **CountryRule** (id, country unique — как в атрибуте «Страна», simType enum esim_only|dual_sim|sim_esim, flag, note, isActive). Витрина/синк выводят атрибут SIM из страны варианта по справочнику, если в листе SIM не задан явно (явное значение листа выигрывает — sheet-канал).
  - API: CRUD `/admin/api/country-rules`.
- **Наличие**: показ остатков (read-only), кнопка «Обновить из таблицы» (есть триггер), журнал SyncRun (§3.3). Ручной приход/расход из бота в веб **не переносим** (рудимент).

### 4.5 Цены и поставщики (дерево §4) — см. §7 (флагман, отдельный раздел)

### 4.6 Продажи (дерево §5)

- **Заказы**: веб-список с фильтрами (статус/дата/поиск), смена статуса, карточка заказа. Всё на существующих Order/OrderItem.
  - API: `GET /admin/api/orders?status=&q=`, `PUT /admin/api/orders/:id/status`.
- **Прибыль**: `Sale.costPrice` собирается — показываем маржу по продажам/периодам. Схема: без изменений, только выборки.
  - API: `GET /admin/api/sales/summary?from=&to=` (выручка, закупка, маржа, по категориям/брендам).
- **Авито как канал**: своя наценка — через `MarkupRule.channel` (§7.4), сверка цен сайт/Авито — отчёт по вариантам с обеими ценами.
  - API: `GET /admin/api/avito/price-diff`.

### 4.7 Аналитика (дерево §6)

События уже пишутся (Event, 1 491; `filter_line` починен PR #16). Не хватает показа.

- **Схема**: индекс `Event(type, createdAt)` при отсутствии; материализация не нужна на текущих объёмах (тысячи строк) — агрегируем на лету; `EventDaily` отложить до реальных объёмов.
- **API**: `GET /admin/api/analytics/funnel?from=&to=` (view_product → add_to_cart → checkout_start → order_created), `GET /admin/api/analytics/timeseries?metric=&granularity=day|week`, `GET /admin/api/analytics/products?metric=views_without_orders` («смотрят, но не покупают»), `GET /admin/api/analytics/export` (CSV).

### 4.8 Автоматика и Система (дерево §7–8)

- **AI-агент**: человеческий тумблер режимов (off/manual/semi/auto) и расписание — обёртка над существующими настройками. API: `GET/PUT /admin/api/ai/settings`.
- **Расписания списком**: рантайм-реестр джобов (синк, акции, бэкап, курс USD) + «последний запуск» из SyncRun/логов. Схема: `JobRun` (id, job, startedAt, finishedAt, ok, note) — лёгкий журнал для всех кронов, SyncRun — его специализация для синка (или SyncRun.details внутрь JobRun; решить при имплементации, важно одно место «что и когда бегало»). API: `GET /admin/api/jobs`.
- **Система**: бэкап-кнопка (есть), режим обслуживания (есть), security-лог (есть) — просто вывести в веб. Массовые удаления — только owner-роль, за двойным подтверждением, глубоко в «Ещё». Орфан «Балансы» — похоронить (кнопку не добавлять).
- **Журнал действий**: **AuditLog** (id, adminId, action, entity, entityId, before Json, after Json, createdAt). Пишется миддлварой на все мутации `/admin/api/*`. Он же — источник «вернуть моё» из §1.2. API: `GET /admin/api/audit?entity=&admin=`.
- **AdminUser** (id, telegramId unique, name, role owner|manager, isActive, createdAt) — см. §2.
- **Тестовый магазин** — вне скоупа этого документа (отдельная среда/деплой, Этап 4+).

## 7. Флагман: парсер прайсов с обучением из админки (дерево §4)

Боль №1 владельца: цены от поставщиков приходят сообщениями 10+ раз в день, разбор ручной. Весь контур уже спроектирован в БД и наполовину написан (`bot/admin/pricing.ts`, `webhooks/supplier.ts`) — но не использовался (0 строк). Оживляем, а не пишем с нуля.

### 7.1 Что переиспользуем

| Существующее | Роль в новой схеме |
|---|---|
| `Supplier` (CRUD в боте готов) | карточка поставщика: имя, чат, наценка по умолчанию, `lastPriceAt` («когда последний раз присылал») |
| `SupplierPrice` | распарсенная строка прайса: модель/память/цвет/SIM/страна/цена + `rawMessage`. Добавляем `batchId` |
| `PriceAlias` (alias → product/variant, `isIgnored`) | память сопоставлений: «как поставщик называет» → наш вариант. Это и есть «обучение» |
| `MarkupRule` (12 живых правил) + `applyMarkupRules` | цепочка закупка → рекомендованная. Добавляем `channel` |
| `PriceChange` | история применений; `batchId` для отката пачкой |
| Writeback синка (`sheetWritebacks`) | доставка новых закупочных и рекомендованных в таблицу |
| Парсер сообщений (pricing.ts / supplier webhook) | разбор текста прайса в структуру |

Новая модель: **PriceApplyBatch** (id, supplierId, source message|file|paste, status `parsing → preview → applied | discarded | rolled_back`, createdBy, appliedAt, stats Json: строк / узнано / не узнано / вне коридора).

### 7.2 Поток (шесть шагов из постановки)

1. **Разобрать.** Источник: пересланное сообщение в бота (существующий webhook), файл или вставка текста в вебе → `POST /admin/api/price-batches`. Парсер раскладывает в SupplierPrice (batchId, неактивные), матчер прогоняет каждую строку: сначала точный `PriceAlias`, затем нормализация имени (переиспользуем подход `lib/photo-match-normalize.ts` — регистр/пробелы/синонимы) против `fullName`/имён вариантов. Результат строки: `matched (variantId)` или `unmatched`.
2. **Предпросмотр.** `GET /admin/api/price-batches/:id` — таблица: вариант · закупка была → станет · розничная была → станет (по цепочке наценки канала) · Δ% · флаг «вне коридора». **Коридор автоприменения ±15% (утверждено §9.1)**: строки в пределах — галочка по умолчанию; за границей коридора — для `manager` строка блокируется до подтверждения `owner`, `owner` включает явно.
3. **Применить.** `POST …/:id/apply` — транзакция: `costPrice` вариантов ← закупка, `price` ← цепочка наценки, PriceChange на каждую строку (batchId), SheetWriteback закупочной и рекомендованной в лист, `Supplier.lastPriceAt = now`, batch → applied. Розничная в БД и листе меняется только через цепочку — ручная правка розницы владельцем в листе по-прежнему сильнее (sheet-канал, §3.2).
4. **Очередь «не узнал».** `GET /admin/api/price-batches/:id/unmatched` + сводная очередь по всем батчам на дашборде. Строку можно: связать (шаг 5), игнорировать навсегда (`PriceAlias.isIgnored` — «это не наш товар»), пропустить.
5. **Связать.** Выбор варианта из поиска → `POST /admin/api/aliases` (alias = нормализованное имя строки поставщика → variantId) → авто-рематч всех unmatched строк очереди этим алиасом → строка переезжает в предпросмотр батча.
6. **Запомнила.** Следующие прайсы этого (и любого) поставщика матчатся по PriceAlias до эвристик. Очередь со временем высыхает — «связал один раз».

### 7.3 Лучшая цена и срок жизни

- **TTL цены**: `Supplier.priceTtlDays` (**по умолчанию 3 — утверждено §9.2**) или `SupplierPrice.expiresAt` при записи. «Свежая» = `parsedAt + TTL > now`.
- **Автовыбор минимальной**: на предпросмотре для варианта показываются свежие цены всех поставщиков, предлагается минимальная; в карточке варианта в админке — блок «цены поставщиков» (кто, почём, когда).
- Протухшие цены из выбора исключаются, но хранятся (история).

### 7.4 Наценка по каналам (сайт ≠ Авито)

`MarkupRule.channel: site | avito` (default site — текущие 12 правил остаются правилами сайта). Цепочка применяется по каналу: розничная сайта → `Product/Variant.price` (+ writeback в лист), цена Авито → считается на лету для выгрузки/сверки (материализация поля `avitoPrice` — только если появится интеграция выгрузки объявлений; до тех пор отчёт §4.6). Правка правил — в вебе (сейчас только бот): CRUD `/admin/api/markup-rules` с предпросмотром «какие цены изменятся».

### 7.5 Откат

`POST /admin/api/price-batches/:id/rollback` — по PriceChange батча вернуть старые цены/закупки, writeback в лист, batch → rolled_back. Откатывается только последний applied-батч, затронувший вариант (иначе — конфликт с более свежими правками, показываем список конфликтных строк).

## 9. Решения владельца по открытым вопросам (утверждено 27.07.2026)

1. **Коридор ±15% — да.** Manager: авто только в коридоре, за границей → подтверждает owner.
2. **TTL цены — 3 дня** по умолчанию.
3. **Writeback контента — не сразу.** Этап 1 и admin-only поля его не требуют. Общие поля (описание/бейдж/порядок) на Этапе 2 — сначала без обратной записи; writeback включается отдельным шагом (2b) после проверки LWW на живых данных. Безопасность таблицы владельца важнее скорости.
4. **Сегменты/теги — убрать поле из карточки** (схему не удалять, просто скрыть). К Этапу 3.
5. **Авито-округление/сверка — отложить** до интеграции выгрузки объявлений.

Этапы 1–4 согласованы, цены — первым.

## 10. Условия безопасности Этапа 1 (владелец, 27.07.2026)

1. **PR-7 (применение + writeback цен) — особый режим.** Первый прогон на проде — **DRY-RUN**: считает и показывает предпросмотр применения, но не пишет ни в таблицу, ни в БД-цены. Флаг снимается только после подтверждения владельцем корректности на реальном батче. Снапшот БД — прямо перед деплоем PR-7 (в дополнение к снапшоту перед PR-1). Откат тестируется на тестовом батче **до** первого реального применения — «откат проверен», а не «кнопка есть».
2. **Роль `manager` реально гейтит с PR-2**, даже пока все админы — owner: иначе коридор-гейт PR-7 не на что опереться.
3. **`prisma db push` — ок для аддитивных изменений сейчас.** На этапах 2–3 завести `prisma migrate` (миграции в репо), чтобы push не срезал данные при расхождении схемы. Сейчас не трогаем — зафиксировано как долг.
