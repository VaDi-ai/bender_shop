# «Рекомендуем»: снапшот и откат

Снято 2026-09-10, до миграции, на ветке `feat/manual-recommendations`.

## Что в снимке

| файл | что это |
|---|---|
| `products-before.json` | ответ `GET https://bendershop.store/api/products` (39 видимых товаров) — эталон ленты до изменений |
| `db-before.txt` | колонки `Product`, счётчик строк (721), хвост `_prisma_migrations` |

В `db-before.txt` зафиксировано главное: колонки `recommendedIds` в проде нет,
последняя применённая миграция — `20260903180000_add_preorder`.

## Как проверить инвариант после деплоя

```
curl -s https://bendershop.store/api/products > reports/recs-2026-09-10/products-after.json
node scripts/recs-invariant-check.cjs \
  reports/recs-2026-09-10/products-before.json \
  reports/recs-2026-09-10/products-after.json
```

Скрипт не сравнивает файлы сырым diff — между снимками проезжает синк, остатки
и цены законно меняются, и такой diff был бы непустым всегда. Вместо этого:

1. **Главный инвариант считается внутри одного снимка**: у товара без ручных
   замен новая ветка `resolveRecs()` обязана дать ровно то же, что старая
   `getRecommendations()`. Синк на это повлиять не может — вход один и тот же.
2. По паре снимков сверяется только форма payload: набор ключей. Ключ
   `recommendedIds` имеет право появиться лишь у товаров с заменами.
3. У товаров с заменами проверяется, что закреплённое встало на свой слот.

Обе функции скрипт берёт из живого `webapp/index.html`. Ненулевой код возврата =
инвариант нарушен.

## Откат

Колонка аддитивная и инертная: пока массив пуст, её никто не читает, а витрина
уходит в старую ветку по первой же строке `resolveRecs()`. Поэтому:

**Обычный откат** — вернуть предыдущий деплой (revert коммита ветки). Колонку
можно оставить: она никому не мешает, и ручные замены переживут повторную
раскатку.

**Полное снятие**, если колонка не нужна совсем:

```sql
ALTER TABLE "Product" DROP COLUMN "recommendedIds";
```

и удалить строку миграции:

```sql
DELETE FROM _prisma_migrations WHERE migration_name = '20260910120000_add_product_recommendations';
```

Данных при этом теряются только ручные замены — ассортимент, цены, фото и
условия предзаказа колонка не трогает.

## Про деплой

Миграция едет `preDeployCommand` (урок PR #112: `releaseCommand` Railway
игнорирует). `UNIQUE` в ней нет — урок #107, из-за которого unique-констрейнт
на старте валил `db push` и гасил контейнер. После деплоя сверить руками:

```sql
SELECT migration_name, finished_at FROM _prisma_migrations ORDER BY finished_at DESC LIMIT 3;
```
